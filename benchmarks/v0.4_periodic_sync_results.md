# V0.4 Periodic Sync Benchmark

Build: Release  
Runs: 5  
Operations: 20,000  
Transport: localhost TCP, synchronous request/response  
Persistence: append-only log with periodic `fdatasync()`

The benchmark measures the effect of different periodic sync intervals on end-to-end server performance.

`max_unsynced` is the largest observed number of commands appended since the previous completed sync. It represents the size of the potentially vulnerable tail at that point in the run.

## Observations

Very short sync intervals are dominated by the cost of `fdatasync()`. At 1 ms, throughput falls to roughly 6–9K operations/s and sync stalls appear directly in the p99 latency.

Increasing the interval substantially improves throughput:

```text
1 ms   -> ~6-9K ops/s
5 ms   -> ~32K ops/s
10 ms  -> ~56-58K ops/s
20 ms  -> ~69-73K ops/s
```

The tradeoff is a larger unsynchronized tail. At 20 ms, the maximum observed unsynced command count rises to roughly 1,500 commands.

A 10 ms interval provided a reasonable measured tradeoff on this machine: around 56–58K operations/s while keeping the observed maximum unsynced tail around 600 commands.

This should not be interpreted as a universally optimal interval; the result depends on workload, storage, operating system, and request rate.
